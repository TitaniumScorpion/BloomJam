## Verify every change without opening Unity

The project compiles offline against the Unity DLLs in ~4 seconds. **Always run this after
editing scripts** — do not hand back unverified code:

```bash
dotnet build Assembly-CSharp.csproj -v q --nologo
```

Two things to know:

- **MSBuild output is Turkish.** `Hata` = error, `Uyarı` = warning,
  `Oluşturma başarılı oldu` = build succeeded. Grep for `error CS` / `warning CS` to be safe.
- **New `.cs` files fail until registered.** `Assembly-CSharp.csproj` lists every file
  explicitly and is regenerated by Unity (it is gitignored — safe to patch locally). Add a
  `<Compile Include="Assets\Scripts\YourFile.cs" />` line to build offline before Unity has
  seen the file.

Keep the build at **0 warnings**. It was cleaned to zero deliberately, so a new warning is a
real signal rather than noise.

## Unity serialization — read before restructuring any script

Unity stores component values by **public field name**, walking the whole inheritance chain.

- ✅ **Safe:** adding interfaces, extracting base classes, moving a field to a base class,
  changing method bodies, adding private fields. Inspector values survive.
- ⚠️ **Silently destructive:** renaming a public field (its value resets), or moving a `.cs`
  without its `.cs.meta` (new GUID → every prefab reference breaks).
- ❌ **Loudly destructive:** deleting or renaming a script class → "Missing script" on every
  prefab using it.

**After moving fields between classes, verify the field set is unchanged** rather than assuming.
Diff the public field names of the old version against base + derived — that check caught
nothing twice, which is exactly why it is worth running.

Merging two MonoBehaviours that live on different GameObjects breaks scene wiring. Prefer
**base classes and shared helpers**, which get the same deduplication with zero scene risk.

## Architecture invariants

### Bullet time does not use `Time.timeScale`
The player keeps moving at full speed while everything else stops, so **every moving object
freezes itself** by polling `KatanaWeapon.IsBulletTimeActive`.

Any new enemy or projectile **must** handle this or it will keep moving during bullet time.
Use the `BulletTimeFreeze` struct — one field, one `Tick(rb)` call. Exception:
`FlyingChaserEnemy` recomputes velocity each frame, so it just zeroes velocity.

This also constrains any future hit-stop feature — a `timeScale` dip would collide with it.

### Adding an enemy type
1. Implement `IDamageable`, or inherit `FlyingChaserEnemy` (which already does).
2. Call `EnemyEvents.ReportDeath()` on death — otherwise the zone quota never counts it.
3. Handle bullet time (above).
4. Add a pool entry on `ObjectPooler`; `DeactivateAll()` then covers it at zone transitions.

### Player-facing scripts need three gates
`Time.timeScale == 0` (countdown), `!GameManager.HasGameStarted` (pre-run), and
`ElevatorHub.IsActive` (hub browsing). Weapons inherit this via `HandheldWeapon.CanAct()`.

### Progression is single-scene
`GameManager.zones[]` holds zone GameObjects; only the current index is active. `QuotaManager`
state is `static` so it survives scene reloads — reset it via `ResetProgression()`.

## API traps hit in this project

- **`Quaternion == default` is always `false`.** Unity overloads `operator==` to compare by
  dot product, and `Dot(zero, zero) == 0` fails the `> 0.999999f` test. Never use `== default`
  on a Quaternion — use `Quaternion?` and `?? Quaternion.identity`. This shipped a real bug
  that compiled cleanly.
- **The sort-mode enum is `FindObjectsSortMode`**, not `FindObjectSortMode`. Unity's own
  deprecation message contains that typo; copying it will not compile.
- `FindObjectsOfType` / `FindObjectOfType` are deprecated. Use
  `FindObjectsByType<T>(FindObjectsSortMode.None)` and `FindFirstObjectByType<T>()`.

## Working style that fits this project

- **Go one change at a time.** The user keeps Unity open alongside and playtests between
  steps. Land one coherent change, say exactly what to test, then wait.
- **Say what to verify in-editor**, not just that it compiles. Prefab Inspector values and
  enemy behaviour are things only the running game can confirm.
- The user commits after each verified step, so the git diff is a precise map of the current
  change. Do not commit unless asked.
- **The player has 1 HP** (`PlayerHealth.maxHealth = 1`), per the design doc. Every combat
  change is high-stakes to test.
- Blocks marked `YILMAZ KOD MAESTER WAS HERE` (e.g. in `Projectile.cs`) are a collaborator's —
  leave their formatting alone unless the change is specifically about that code.
- When behaviour must stay identical, **"no visible difference" is the success criterion.**
  Most of the refactor work here fixed latent bugs that nothing was surfacing yet.
